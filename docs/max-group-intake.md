# Приём контента из группы MAX

Существующий webhook `POST /api/max/webhook` не заменяется. Секрет по-прежнему проверяется один раз в `handleMaxWebhook`, затем сообщение разрешённой группы попадает в `planGroupUpdate`. Личный сценарий `/review` и команды модератора остаются в диалоге с ботом.

Новая production-подписка этим кодом не создаётся и не изменяется.

## Что сохраняется

Сообщение группы пишется в таблицу `incoming_content` миграции `db/migrations/002_group_content.up.sql`.

- `review` — текст или подпись начинается с отдельного слова «Отзыв». Регистр не важен. Перед словом допускаются пробелы, невидимые символы, эмодзи, знаки препинания и разметка (`🩵Отзыв`, `⬆️ Отзыв:`, `**Отзыв**`, `#отзыв`, `[Отзыв]`). Буквы или цифры перед словом не допускаются, поэтому `Отзывчивый`, `🩵Отзывчивый` и `Наш отзыв` отзывом не считаются. После слова нужен не-буквенный символ или конец текста. Правило описано в `server/max/classify.ts` и проверено `classifyMarker.test.ts`.
- `text`, `image`, `video`, `mixed`, `unsupported` — остальной контент. Он сохраняется, но на сайт сам не попадает.
- `empty` — только слово «Отзыв» без текста и без фото или видео. Такая запись не публикуется.

Повтор того же `message.body.mid` в том же `chat_id` не создаёт вторую строку. `message_edited` обновляет эту строку. Если отзыв уже был на сайте, правка снимает его с публикации и снова ставит в ожидание. `message_removed` помечает запись `removed` и больше не показывает связанный отзыв. У события удаления в схеме MAX поле называется `message_id`; для обычного сообщения это тот же идентификатор, что `body.mid`.

История через `GET /messages` не загружается.

## Медиа

Фото и видео читаются из `attachments[]` как `type: image` и `type: video`. Временный `url` MAX в базу не пишется (SSRF): допускаются только хосты `*.okcdn.ru` и `*.oneme.ru`, и только на время того же запроса.

Если задан `BLOB_READ_WRITE_TOKEN`, webhook скачивает файл и кладёт его в Vercel Blob. В `incoming_content.attachments` остаётся `persistedSrc`. При `/review_approve` эти URL копируются в `product_reviews.media` и отдаются через `GET /api/reviews`. Сайт показывает только пути своего origin и `*.blob.vercel-storage.com`.

Без токена Blob медиа на сайт не попадает — в карточке остаётся текст. Перед одобрением бот может один раз запросить свежие вложения через `GET /messages`, если URL в webhook уже истекли.

Вложение другого типа не останавливает обработку. Его токен и адрес не сохраняются, запись получает тип `unsupported` либо остаётся у допустимого текста и медиа.

## Модерация

Публикация по-прежнему только из личного диалога и только для `MAX_REVIEW_MODERATOR_IDS`.

- Групповой отзыв с текстом: `/review_approve <id> <productId>`. `productId` берётся из `src/data/products.ts`.
- Отзыв из диалога, как раньше: `/review_approve <id>`.
- `/review_reject <id>` отклоняет и диалоговый, и групповой отзыв.
- Фото или видео с одной подписью «Отзыв» остаётся в `incoming_content`, но на сайт не публикуется без публичного текста.

Идентификатор отправителя группового сообщения в базу не пишется.

## Переменные

К уже существующим `MAX_BOT_TOKEN`, `MAX_WEBHOOK_SECRET`, `MAX_REVIEW_MODERATOR_IDS` и `DATABASE_URL` добавляются:

```text
MAX_ALLOWED_CHAT_IDS=
BLOB_READ_WRITE_TOKEN=
```

Это числовые `chat_id` через запятую, в том числе отрицательные идентификаторы групп. Пустое или неверное значение не принимает ни одну группу. Значение по умолчанию, которое открывало бы все чаты, не задаётся.

`chat_id` группы заранее не подставлен. Его можно увидеть в `message.recipient.chat_id` у `message_created` или в `chat_id` события `bot_added`. Проверка конкретного чата: `GET /chats/{chatId}` с заголовком `Authorization: <token>`.

Чтобы бот видел обычные сообщения группы, а не только обращения к себе, у него должно быть право администратора `read_all_messages`. Список администраторов: `GET /chats/{chatId}/members/admins`. Код проверяет это право на переданном списке разрешений и не вызывает API сам.

## Подписка

Действующий webhook менять не нужно, пока достаточно `message_created`. Редактирование и удаление дойдут только если в той же подписке есть `message_edited` и `message_removed`. Повторный `POST /subscriptions` меняет боевую подписку, поэтому его выполняет оператор вручную и сохраняет прежние `url` и `secret`.

## Миграция

```bash
npm run db:migrate -- up
npm run db:migrate -- down
```

Откат удаляет `incoming_content` и отзывы сайта, опубликованные из группы (у них нет `sender_user_id`). Отзывы из личного сценария остаются. Команда не запускается без `DATABASE_URL`.

## Локально

`npm run dev:api` по-прежнему держит данные в памяти и не ходит в MAX. Для проверки группы в этом процессе задайте `MAX_ALLOWED_CHAT_IDS`. `npm run dev` сам webhook не обслуживает.

## Что не подтверждено

Реальная группа, права администратора и доставка боевых webhook в этом репозитории не проверялись. Пока нет `DATABASE_URL` и `MAX_ALLOWED_CHAT_IDS` на сервере, группа в production не читается.

## Диагностика

Webhook пишет по одной JSON-строке на этап (без текста сообщений, токенов и ссылок на медиа):

- `group_intake` — `kind`, `allowed` (чат разрешён или нет), `attachments` (число), `duplicate`;
- `storage_failed` — класс ошибки и код (`errorClass`), ответ `503`, чтобы MAX повторил доставку;
- остальные события — `unauthorized`, `ignored` и т. п. (см. `server/max/logger.ts`, список разрешённых полей).

Скачивание медиа в Blob при приёме ограничено бюджетом 12 с, чтобы не задерживать ответ MAX (лимит MAX — 30 с).

## Просмотр записей без маркера

`/content_pending` (только модератор из `MAX_REVIEW_MODERATOR_IDS`) показывает ожидающие записи группы, которые не стали отзывами (kind text/image/video/mixed). Команда только читает. `/reviews_pending` показывает только kind=review. Опубликовать запись без маркера нельзя: `/review_approve` работает с kind=review.

Разовая переклассификация уже сохранённых ожидающих записей (идемпотентна, ничего не публикует, текст не печатает): `npx tsx --env-file=.env.local scripts/reclassify-pending.ts [--apply]` (без `--apply` это dry-run).

## Меню модератора и кнопки

Модератор — пользователь, чей MAX `user_id` есть в `MAX_REVIEW_MODERATOR_IDS`. Команды модератора обрабатываются раньше сценария клиента: черновик `/review` при этом не теряется.

- `/start`, `/help`, `/menu`, `/moderate` в личке: у модератора — меню с кнопками «Очередь отзывов» и «Все ожидающие сообщения», у остальных — обычная справка (`/menu` и `/moderate` для них — «Команда недоступна.»).
- Под каждой записью очереди — «Опубликовать» (для группового отзыва открывается выбор товара кнопками) и «Отклонить». Прочие записи группы можно только отклонить.
- Команды `/reviews_pending`, `/content_pending`, `/review_approve`, `/review_reject` работают по-прежнему.
- Кнопки: `m:q`, `m:c`, `m:x`, `m:a:<uuid>`, `m:r:<uuid>`, `m:n:<uuid>:<страница>`, `m:p:<uuid>:<productId>`. Любой другой payload отвергается; каждый вызов проверяется по `MAX_REVIEW_MODERATOR_IDS`, нажатия в группе не обрабатываются.
- Опечатка в команде у модератора даёт справку и меню.

### Как узнать свой user_id

В личке с ботом: `/whoami` или `/moderator_id`. Ответ содержит только `user_id` отправителя. В группе команда не отвечает. Добавьте номер в `MAX_REVIEW_MODERATOR_IDS` (несколько — через запятую) и **запустите новый деплой**: Vercel применяет изменения переменных только к новым деплоям.

## Меню команд MAX

Список команд в интерфейсе MAX задаётся отдельно (`PATCH /me/commands`) и общий для всех пользователей бота. Скрипт запускает владелец бота со своим токеном, токен остаётся в его сессии и не печатается:

```powershell
$env:MAX_BOT_TOKEN = '<токен бота>'
node scripts/max-set-commands.mjs --dry-run          # показать, что будет отправлено
node scripts/max-set-commands.mjs                    # /start /review /cancel /whoami /help
node scripts/max-set-commands.mjs --with-moderation  # + /menu /reviews_pending /content_pending (их увидят все пользователи, выполнит только модератор)
node scripts/max-set-commands.mjs --clear            # убрать меню
```

Даже без меню команды можно набрать вручную.

## Удаление сообщений группы

Событие `message_removed` содержит `chat_id` (число, у групп отрицательное), `message_id` (строка, совпадает с `mid` сообщения) и `user_id`. В событии нет типа чата, поэтому удаления в личных диалогах и чужих чатах тоже попадают в `group_intake` с `allowed:false`, их запись не затрагивается. В `group_intake` добавлены безопасные поля `chatType` (dialog/chat/channel/unknown) и `chatSign` (negative — группа, positive — личный диалог, none): сами id чатов не логируются.
## Сборка функций

`api/max/webhook.js` и `api/reviews.js` — закоммиченные бандлы (`npm run bundle:api`), `npm run build` их не пересобирает. Бандл ESM, а `pg` и часть зависимостей CommonJS, поэтому `scripts/bundle-api.mjs` добавляет баннер `createRequire`. Без него функция падала при загрузке («Dynamic require of "node:buffer" is not supported») и отвечала 500 на любой запрос. Регрессию ловит `bundleSmoke.test.ts` (запускает бандл в отдельном процессе из .mjs-файла; `node -e` не годится, у него есть глобальный `require`). После правок в `server/` пересоберите бандлы и закоммитьте их.
