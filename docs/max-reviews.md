# Импорт отзывов из MAX

Сайт по-прежнему статический Vite-фронтенд и деплоится на Vercel (`silkwaysitefortanya.vercel.app`). Полноценной CMS, панели администратора и уже подключённой базы в репозитории нет. Отзывы не хранятся в JSON-файле и не пишутся в файловую систему функции.

Боевой импорт заработает только после трёх отдельных шагов оператора: создать PostgreSQL, применить миграцию и зарегистрировать HTTPS webhook. Пока этого нет, код отвечает отказом и не считает событие принятым.

## Архитектура

```text
MAX  --HTTPS POST-->  api/max/webhook.ts  --SQL-->  PostgreSQL
браузер --GET-->      api/reviews.ts      --SQL-->  только status = published
страница товара -->   CmsClient.listReviews({ productId })
```

Общая логика лежит в `server/max/`, а не в `src/integrations/telegram`. Telegram-заглушка остаётся клиентской и не становится шлюзом MAX.

Vercel для Node.js создаёт функцию из каждого файла в корневом `api/`. Поэтому в `api/` только две точки входа:

- `api/max/webhook.ts` — `POST` событий MAX;
- `api/reviews.ts` — `GET` опубликованных отзывов.

Оба файла экспортируют Web-обработчик `fetch`, как в текущей документации Vercel для Node.js. Общие модули лежат вне `api/`, чтобы не стать отдельными публичными функциями.

`GET /api/reviews` не создаёт отзыв. `POST /api/reviews` отвечает `405`.

## Путь события

1. Пользователь пишет боту в личном диалоге. MAX доставляет `Update` на `https://<домен>/api/max/webhook`.
2. Функция принимает только `POST`, ограничивает тело 256 КиБ и требует `Content-Type: application/json`.
3. Секрет из `MAX_WEBHOOK_SECRET` сравнивается с заголовком `X-Max-Bot-Api-Secret` через SHA-256 и `timingSafeEqual`. Неверный, пустой или не настроенный секрет даёт `401`. Адрес отправителя, имя и текст сообщения подлинность не подтверждают.
4. Обрабатываются только `bot_started`, `message_created` и `message_callback`. Остальные типы подтверждаются `200` и не сохраняются. Схема сверена с `schema.yaml` репозитория `max-messenger/api-schema`: у каждого `Update` обязательны `update_type` и `timestamp`.
5. Ключ идемпотентности строится из документированных полей: `message_created:<timestamp>:<message.body.mid>`, `message_callback:<timestamp>:<callback.callback_id>`, `bot_started:<timestamp>:<chat_id>:<user_id>`. Повтор вставляется в `max_update_receipts` с `ON CONFLICT DO NOTHING` и не создаёт второй отзыв.
6. Сценарий `/review` идёт в одной транзакции: выбор товара из `src/data/products.ts`, текст, необязательное имя, явное согласие. Без согласия строка отзыва не создаётся.
7. Ответ пользователю пишется в `review_outbox` в той же транзакции. После коммита функция отправляет его в `https://platform-api2.max.ru` заголовком `Authorization: <token>`. Токен в URL не передаётся. Редиректы не следуют. Проверка TLS не отключается.
8. `200` возвращается после записи и успешной отправки ответа. Ошибка базы или временная ошибка MAX (`401`, `408`, `429`, `5xx`, сеть) даёт `503`, чтобы MAX повторил доставку. Повтор не дублирует отзыв и доотправляет неотправленный ответ.
9. Модератор в личном диалоге вызывает `/reviews_pending`, `/review_approve <id>` или `/review_reject <id>`. Идентификатор сравнивается с `MAX_REVIEW_MODERATOR_IDS`. Username не используется. Пустой или неверный список запрещает все три команды.
10. Сайт запрашивает `GET /api/reviews?productId=<id товара>`. `CmsClient` кладёт в модель только `id`, `productId`, `author` и `text`. Страница товара рисует их как текст React, без `dangerouslySetInnerHTML`.

## Сценарий бота

- `/start` и событие `bot_started` объясняют, как оставить отзыв.
- `/review` показывает товары каталога кнопками. Идентификатор кнопки проверяется по живому каталогу.
- Текст — одно сообщение без вложений, до 2000 символов. Вложения в этой версии не скачиваются и не сохраняются.
- Имя необязательно и короче 80 символов. Телефон и адрес не запрашиваются.
- Кнопки «Согласен на публикацию» и «Не публиковать» фиксируют согласие. Отказ удаляет черновик.
- После согласия отзыв остаётся `pending`. Бот прямо говорит, что это ещё не публикация.
- `/cancel` или кнопка «Отмена» удаляет черновик.
- Черновик живёт 30 минут. Повторная доставка того же события не сдвигает сценарий второй раз.

## Хранилище

Миграция `db/migrations/001_reviews.up.sql` создаёт:

- `max_update_receipts` — ключ идемпотентности;
- `review_sessions` — незавершённый диалог и срок жизни;
- `product_reviews` — отзыв, согласие, статус, модератор и отправитель MAX;
- `review_outbox` — ответы, которые ещё нужно отправить в MAX;
- `review_intake_events` — счётчик частоты, без текста сообщения.

`sender_user_id` и `moderator_user_id` нужны для ограничения частоты и аудита решения. Публичный `SELECT` их не возвращает.

Применение и откат, когда `DATABASE_URL` уже задан в окружении команды:

```bash
npm run db:migrate -- up
npm run db:migrate -- down
```

Откат удаляет только таблицы этой интеграции. Таблица `schema_migrations` остаётся. Команда не запускается автоматически при деплое и не выполняется, если `DATABASE_URL` пуст. Провайдера базы этот репозиторий не выбирает и аккаунт не создаёт.

Локальные тесты подменяют хранилище памятью процесса. `npm run dev:api` тоже держит отзывы только в памяти и не вызывает MAX. Это не production-хранилище: после остановки процесса отзывы исчезают.

## Окружение

В `.env.example` только пустые имена. Файл `.env` игнорируется Git.

| Переменная | Где | Назначение |
| --- | --- | --- |
| `MAX_BOT_TOKEN` | только сервер Vercel | заголовок `Authorization` для `platform-api2.max.ru` |
| `MAX_WEBHOOK_SECRET` | только сервер, тот же секрет в `POST /subscriptions` | заголовок `X-Max-Bot-Api-Secret` |
| `MAX_REVIEW_MODERATOR_IDS` | только сервер | числовые `user_id` через запятую |
| `DATABASE_URL` | только сервер | PostgreSQL, желательно `sslmode=require` |

Не добавляйте префикс `VITE_`. Сборка браузера такие переменные не читает. Если Node не доверяет сертификату Минцифры на хосте API, добавьте корневой сертификат через `NODE_EXTRA_CA_CERTS`. Не устанавливайте `NODE_TLS_REJECT_UNAUTHORIZED=0`.

Секрет webhook: 5–256 символов из `A–Z`, `a–z`, `0–9`, `_` и `-`.

## Регистрация webhook

Делайте это вручную, когда функция уже открыта по HTTPS на порту 443 с доверенным сертификатом и переменные заданы в Vercel. Этот репозиторий регистрацию не выполняет.

```bash
curl -X POST "https://platform-api2.max.ru/subscriptions" \
  -H "Authorization: $MAX_BOT_TOKEN" \
  -H "Content-Type: application/json" \
  -d "{\"url\":\"https://<домен>/api/max/webhook\",\"update_types\":[\"message_created\",\"message_callback\",\"bot_started\"],\"secret\":\"$MAX_WEBHOOK_SECRET\"}"
```

Long polling (`GET /updates`) для production не используется и в этот код не встроен: он взаимно исключается с webhook. Локально сценарий проверяется модульными тестами и `npm run dev:api`, а не опросом платформы.

Проверка текущего списка: `GET /subscriptions` с тем же заголовком. Удаление: `DELETE /subscriptions?url=<url>`.

Если секрет или токен утёк:

1. Выпустите новый токен в настройках бота MAX и удалите старый.
2. Смените `MAX_WEBHOOK_SECRET` в Vercel и заново вызовите `POST /subscriptions` с новым секретом.
3. Смените пароль базы в `DATABASE_URL`, если есть риск, что он был рядом с токеном.
4. Посмотрите `product_reviews` со статусом `pending`, созданные после инцидента, и отклоните сомнительные через `/review_reject`.

## Локальная проверка

Обычный `npm run dev` отдаёт интерфейс Vite. Сам по себе он не принимает webhook: запросы `/api` проксируются на `127.0.0.1:3001`.

```bash
# значение только для этого процесса, в файл его класть не нужно
$env:MAX_WEBHOOK_SECRET = "local-test-secret"
$env:MAX_REVIEW_MODERATOR_IDS = "42"
npm run dev:api
npm run dev
```

В PowerShell переменные выше живут в текущем окне. `dev:api` печатает только адрес, не секрет и не текст отзыва. Ответы бота в этом режиме никуда не отправляются.

На Vercel те же маршруты обслуживают функции `api/`. Без `DATABASE_URL` они отвечают `503` на событие, которое нужно сохранить, и на чтение отзывов.

## Модерация

Команды работают только из личного диалога и только для `user_id` из `MAX_REVIEW_MODERATOR_IDS`.

- `/reviews_pending` показывает до трёх ожидающих отзывов и их id.
- `/review_approve <uuid>` переводит `pending` в `published`.
- `/review_reject <uuid>` переводит `pending` в `rejected`.

Повторное решение не меняет уже закрытый отзыв. Неопубликованные записи в `GET /api/reviews` не попадают.

## Ограничения и остаточные риски

- Компрометация сервера Vercel или `DATABASE_URL` раскрывает токен, секрет, тексты отзывов и идентификаторы MAX. Секрет webhook позволяет прислать поддельное событие от имени пользователя; публикация всё равно требует модератора, но модераторский `user_id` внутри подлинного с точки зрения секрета события тоже можно подделать.
- Идентификаторы MAX читаются из JSON как числа. Значения вне безопасного целого JavaScript отклоняются, а не усекаются.
- `bot_started` дедуплицируется по `timestamp`, `chat_id` и `user_id`. Отдельного id доставки у платформы нет.
- Между успешной отправкой в MAX и удалением строки outbox процесс может упасть. Повтор иногда пришлёт то же подтверждение ещё раз. Второй отзыв при этом не создаётся.
- Частота ограничена 20 событиями на пользователя за 10 минут в базе. Это не заменяет общий лимит 30 запросов/с к API MAX.
- Вложения, видео, документы, вебинары и новости не принимаются. Точка расширения — `server/max/contentRegistry.ts`: у отзыва отдельные разрешение (`dialog-participant`), правило публикации (`explicit-consent-and-moderator`) и запрет вложений. Новый тип добавляется своим обработчиком, а не веткой в браузерной шине Telegram.
- Автоматической публикации нет. Панели администратора нет.
- CSRF для webhook не применяется: сессии cookie нет, запрос подтверждается секретом. Чтение отзывов — `GET` без изменения состояния. XSS снижается тем, что текст не вставляется как HTML. SSRF на нашей стороне закрыт фиксированным хостом `platform-api2.max.ru` и отказом следовать редиректам. SQL идёт только с параметрами `$1…`.

Проверенные средства на машине разработки: ESLint проекта и `npm audit`. Gitleaks, OSV-Scanner, Semgrep, CodeQL и OWASP ZAP в окружении не установлены и намеренно не ставились. OWASP ASVS и Top 10 использованы как чеклист границ, а не как сертификат. Система не заявляется полностью защищённой.
